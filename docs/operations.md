# 更新・バックアップ・復元

このページはサーバー管理者向けです。管理者の画面操作は[使い方](usage.md)、最初の設置は[導入](install.md)を参照してください。例のフォルダー名・プロジェクト名・URLは、自分の設定に合わせます。

各コマンドは、値を表示せずに秘密ファイルを読みます。`set -x`、設定全体の表示、DB接続文字列の貼り付けは行わないでください。停止したときはデータや鍵を削除せず、同じ設定で再開します。

## 何を、どこに残すか

| 保存するもの | 保存先・期間 |
| --- | --- |
| DBバックアップ | 専用読取ロールで取得し、公開鍵で暗号化して、アプリサーバーと別サーバーへ保存します。この版の保管期間は30日で、バックアップ成功時に古い世代を整理します |
| 最新の削除台帳 | DBバックアップとは別の暗号化鍵で、別サーバーへ先に保管します。氏名やQRを含めません。世代は自動削除しません |
| 復号鍵 | 上の保存先とは別の安全な場所へ保管します。DBバックアップ用と削除台帳用を分け、残す世代に必要な旧鍵も保持します |
| 保守の結果 | 管理画面の「稼働状況」で最終バックアップ日時、「保存と削除」で保持処理と削除の状態を確認します |

30日という期間は、バックアップが成功し、古い世代の整理を実行できている場合の値です。ジョブが停止したままなら、古いファイルは残り得ます。設置先で別途コピーしたもの、ディスクのスナップショット、保管先自体のバックアップにも施設側の削除方針を適用してください。期限経過を確認せず「すべて消去した」と案内しないでください。

この版のバックアップ転送上限は、暗号文1件256MiBです。DBのcustom形式dumpも256MiBまでに制限します。大容量・大量データの運用はこの方式の対象外として扱い、容量に対応した保管方式を検討してください。バックアップは取得中に受付APIを一時停止し、この処理が止めた同じAPIだけを戻します。

## バックアップを取る

```sh
sudo python3 /opt/inout/releases/0.1.0-dev.m06/source/scripts/operations.py --config /etc/inout/operations.json backup
```

「暗号化と別サーバーへの保管を確認しました」と表示されたら、保管IDと実行日を控えます。外部保管先から読み戻した指紋まで確認して初めて成功とします。取得だけでは、復元できることの確認にはなりません。

復元には、設置先の識別ID・保管ID・対応する配布物の版が必要です。専用保管先の `last-backup.json` に秘密の内容を含まない情報を記録します。台帳や暗号文を手動で別のフォルダーへ移しただけでは、最新の外部保管を完了した扱いにはなりません。

## 削除が保留になった場合

```text
削除の受付 → DBへ削除指示を保存 → 別サーバーへ暗号化台帳を確定
                                      ↓ 確認できた場合だけ
                             個人情報を消去 → 画面で完了
```

画面で削除を受け付けた時点では、まだ個人情報は消えていません。サーバー管理者は、別サーバーの接続・容量・アクセス権を確認し、次のコマンドで再試行します。

```sh
sudo python3 /opt/inout/releases/0.1.0-dev.m06/source/scripts/operations.py --config /etc/inout/operations.json maintenance
```

未退室の記録などが原因なら、施設の管理者が状況を確認します。DBの処理済み欄や削除台帳を直接書き換えて、完了表示へ変更しないでください。通常APIには、削除指示を消したり処理済みへ書き換えたりする権限を与えていません。

## 更新する

1. 新しい配布物を別のフォルダーへ展開し、配布元と指紋を確認します。今動いている配布物は上書きしません。
2. `/etc/inout/operations.json` の `release` を、新しい配布物の絶対パスへ変更します。プロジェクト名、保管先、URL、秘密情報は引き継ぎます。
3. 新しい配布物のコマンドで診断と更新を実行します。既存の管理者へ、受付を一時停止することを知らせます。

```sh
sudo python3 /opt/inout/releases/0.1.0-dev.m06/source/scripts/operations.py --config /etc/inout/operations.json diagnose
sudo python3 /opt/inout/releases/0.1.0-dev.m06/source/scripts/operations.py --config /etc/inout/operations.json update
```

更新は、受付停止、暗号化バックアップの外部保管、専用移行ロールによるDB移行、最新台帳の確認、アプリ起動の順です。DBや既存の鍵を作り直しません。途中で止まったら、同じ設定・同じコマンドで再開します。移行後に、古いAPIだけを自動で戻すことはしません。

この版が扱う移行元は、配布ソースの最初の5世代と完全一致するM05のDB、または6世代のM06のDBです。M05からの初回更新は、削除機能を公開する前に新しい設置先IDを記録してバックアップと結び付けます。6世代の既存台帳を空に戻すことはありません。他の世代・変更済み移行ファイル・由来不明のDBは自動更新を止めます。

更新後は、管理者がログインできること、既存の在室・履歴を読めること、受付用QRの入室・退室を確認してください。新しい配布物を使うよう、自動保守の設定も管理者が確認します。既存タイマーと異なる設定を自動上書きしないため、以前のジョブの停止と差し替えは明示的に行います。

## DBの資格情報だけを交換する

```sh
sudo python3 /opt/inout/releases/0.1.0-dev.m06/source/scripts/operations.py --config /etc/inout/operations.json rotate-db app
```

最後の `app` は、通常API用です。移行用は `migrate`、バックアップ用は `backup`、保持・削除用は `maintenance` を選びます。まずバックアップを取り、対象ロールのDB側パスワードとファイルを合わせ、新資格の接続と旧資格の拒否を確認します。交換途中に停止しても、同じ対象で再実行します。

ファイルだけを手動で上書きしても、既存PostgreSQLのパスワードは変わりません。この操作ではパスキー、認証サーバーの秘密、バックアップの鍵をまとめて交換しません。DB初期管理者の資格や認証用秘密の交換は、影響を確認した個別の管理作業として扱います。

## 空の別環境へ復元する

復元は、既存のDBを上書きする操作ではありません。新しい専用プロジェクト・保存先・内部ポートを用意します。切り替え前に元の環境の受付・管理操作・自動保守を停止し、同じ設置先を2つの環境で同時稼働させないでください。復元先を外部公開する前に、次の順番を守ります。

```text
新しい環境の準備 → バックアップを復号 → DBを復元 → 最新の外部削除台帳を再適用
                                                          ↓
旧セッション・パスキー・復旧コード・QR・受付資格を無効化 → 公開開始 → 管理者復旧と受付再準備
```

1. バックアップと同じ版の固定配布物を展開し、新しい環境で[導入](install.md)の `configure` まで実施します。`install` はまだ実行しません。新しいDB用・認証用の秘密を生成し、バックアップ内の古い資格をそのまま復活させません。
2. 外部保管先は元の最新台帳があるサーバーへ接続します。新規の空フォルダーや、古い台帳のコピーに切り替えないでください。
3. 必要な復号用秘密鍵を、復元する間だけ、root所有0600で安全に受け渡します。パスフレーズ付き鍵は対話端末で実行し、表示された入力欄へ入力します。入力内容は表示せず、専用のパイプでGnuPGへ渡します。パスフレーズをコマンド引数やログへ書かないでください。
4. 記録した設置先ID・保管IDを指定します。次の `設置先ID`・`保管ID` は実際の記録に置き換えます。

```sh
sudo python3 /opt/inout/releases/0.1.0-dev.m06/source/scripts/operations.py --config /etc/inout-restored/operations.json restore-check --deployment-id 設置先ID --backup-id 保管ID --backup-key /安全な一時保管先/backup-private.asc --ledger-key /安全な一時保管先/ledger-private.asc
```

全表の件数・内容の指紋を照合し、バックアップより後に確定した削除指示も適用します。過去のセッション、パスキー、復旧コード、QR、受付端末の資格は使えなくします。途中で止まった場合は、同じ設定・同じ保管IDで再実行します。最新台帳がない、古い、由来が異なる、取得できない場合は公開を開始しません。

削除済みの利用者に、バックアップ時点で未退室の記録があった場合、個人情報を消して「削除済み利用者」として保持します。退室時刻を勝手に補いません。管理者が実際の状況を確認して、終了または取消を行います。

5. 「隔離復元と削除台帳の再適用が完了しました」を確認してから、公開開始します。この時点でもう一度、外部の最新世代を照合します。

```sh
sudo python3 /opt/inout/releases/0.1.0-dev.m06/source/scripts/operations.py --config /etc/inout-restored/operations.json publish-restore
```

6. HTTPSの接続先を復元先へ向けた後、サーバー管理者が本人確認の上で、[復旧コードの発行](usage.md#サーバー管理者が復旧コードを発行する)を行います。管理者本人が新しいパスキーを登録します。以前のコードは使用できません。
7. 必要な利用者のQRを再発行し、受付端末を申請し直して承認します。架空の利用者で入室・退室を確認します。名簿・在室・履歴と、削除済み利用者の表示も確認します。
8. 復元時に持ち込んだ復号鍵を通常サーバーから取り除き、元の別保管を維持します。新しい環境の自動保守・バックアップも設定します。

M05世代のバックアップは、初回M06更新が記録した識別子に結び付くものだけ扱います。由来不明の古いdumpを復元し、新しい空の台帳を作って公開する操作は、このコマンドでは行いません。
